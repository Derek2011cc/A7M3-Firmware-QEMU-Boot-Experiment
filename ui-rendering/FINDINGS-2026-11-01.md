## 1. 命令模板：绘制包 = 固定模板 + 按绘制打补丁

在 `libObj.so` 的 `.data`（文件偏移 `0x127daa4`，运行时 vaddr `0x1285aa4`）找到一段
**静态命令模板**，按 `(op<<16)|0xf000` 解析共 127 对，结构如下（节选）：

| op | 模板值 | 说明 |
|---|---|---|
| `0x0041` | 0 | 模式 |
| `0x0042` / `0x0043` | `0x43280000` / `0x43600000` = 168.0 / 224.0 | 半宽 / 半高 |
| `0x0047` | `0xfe40feb0` = (-336,-448) | 矩形左上（虚拟坐标） |
| `0x0048` | `0x01c00150` = (336,448) | 矩形右下 |
| `0x0049` | `0x01c00150` | 区域尺寸：低 16=W=336，高 16=H=448 |
| `0x0113` | `0x01c00150` | 目标表面尺寸 |
| `0x0203` | 0 | 索引缓冲地址（绘制时补） |
| `0x0216` | `0x80033330` | 常量块（绘制时补） |
| `0x0580..0x05dd` | 纹理块默认值 | `0x0583=0x00010001`、`0x0584=0x11`、`0x058f=0x19` |
| `0x0589` | `0x1004fe70` | 默认纹理地址（绘制时补） |
| `0x0458` | `0x36` | 后随 28 个 `0x0459` 数据字（属性/常量流） |
| `0x0460/0x0461` | 10 对 | 独立浮点常量（0.00955、0.01123 等） |
| `0x0450..0x0454` | 多组 5 字 | uniform/纹理级参数 |

模板中**没有** `0x0112`（目标表面）、`0x0116`（源表面）、`0x0202`（draw）、
`0x0203`（索引）、`0x0216`（常量块）、`0x0589`（纹理）——这些正是每个 draw 由
构建函数补进去的字段。**这给出了构建函数必须写哪些字段的清单**，也是下一步静态
定位构建函数的最好锚点。

## 2. 坐标变换已证实

两组独立数据：

| 来源 | `0x0042/0x0043` | `0x0049` | `0x0047/0x0048` |
|---|---|---|---|
| 模板 | 168.0 / 224.0 | 336×448 | (-336,-448)–(336,448) |
| 块 22（全屏背景） | 320.0 / 240.0 | 640×480 | (-640,348)–(640,480) |

规律：

```text
W = 0x0049 & 0xffff          H = 0x0049 >> 16
0x0042 = W/2                 0x0043 = H/2
pixel_x = (vx + W) / 2       pixel_y = (vy + H) / 2
```

即虚拟坐标范围是 `[-W,W]×[-H,H]`（2× 坐标），屏幕像素是它的一半。
之前 `A7M3_SUGI_CENTER=1` 写死 `640/480` 只对全屏包成立；模板证明存在
336×448 等其它区域，**正确做法是从 `0x0049` 取 W/H**。

## 5. 负结果：gdbstub 观察点抓不到构建函数

- 在命令缓冲首字下 `Z2` 写观察点；第一次命中 `PC=0x045902f0`（libc 拷贝/清零），
  `r0=命令缓冲 VA`、`r2=0xc8`；
- 继续（`c`）后**反复命中同一条 store**（同一 PC、同一寄存器），即使先 `s` 单步，
  返回的仍是 `watch:` 停止包；
- 100 次命中后放弃。原因判断：QEMU 在该 store 上先触发观察点、单步后重新执行同一
  指令，观察点仍生效；需要在 QEMU 侧记录**写者 PC**（在 Sugilite MMIO 或 RAM
  写路径上加日志），或改用“命中后临时断到 memset 返回地址”的方法。

## 8. 追加：菜单 kick 的调用栈与提交路径（2026-11-01 续）

用 QEMU gdbstub 在 `sugilite kick`（libObj+`0x73a290`）下 `Z0`，命中一次真正的
菜单包（job 首字 `0x0041f000`、count `0x72`）时：

```text
pc=06b1c290 lr=06b1c6e7 job=0a935cec job0=0b445400 job1=20549400 job2=00000072
```

- `LR = base+0x73a6e7`：kick 的直接调用点；
- 栈上还有 `base+0x73bd1d`、`base+0x73aa5d`、`base+0x748df1`（pthread 线程入口方向）；
- job 结构：`[0]=命令缓冲 VA`、`[1]=命令缓冲 PA`、`[2]=命令字数`。

提交函数（`0x73a6d0` 一带）逻辑：

```asm
ldr r2,[r4,#0x44]     ; count
cmp r2,#0
beq  skip
add r0,r4,#0x3c       ; job = &desc->va
bl  0x73a290          ; kick(): 0x1804=job[1]=PA, 0x1800=job[2]=count
```

**更正**：`0x1800` 不是固定常数 `4`，而是**本次命令的字数**（早期小包为 4，
菜单包为 `0x72`）。这一点对理解 kick 语义很重要。

## 9. 追加：纹理直方图说明格式就是 16bpp RGBA4444

对绘制时刻纹理做 16 位值直方图：

| 纹理 | 主要值 | 解释（RGBA4444，A 低 4 位） |
|---|---|---|
| 640×72 文字条 | `0x000f` × 41222、`0x999f` × 640、`0x333f`/`0x444f`… | 黑（R=G=B=0,A=F）+ 灰字（9/9/9,F） |
| 8×16 字形 | `0xfff0` × 56、`0xdddf` × 27、`0x0000` × 25 | 透明白 + 灰不透明 + 全透明 |
| 64×56 图标 | `0x000f` × 3264、`0x999f` × 64 | 黑底 + 灰条 |

结论：**通道顺序不是问题**（RGBA4444 能自洽解释所有常见值）。文字之所以不可读，
原因在别处：

1. 这些文字条本身是 **8px 点阵**（菜单里的小号标签/数值），并非大标题；
2. 大块文字可能由 **shader/属性流**（`0x0458/0x0459`）合成，或画到**工作表面**
   `0x0116` 后再合成，当前渲染器只做“整张纹理拉伸/平铺 + source-over”；
3. `296×48` 这类“标签”纹理 99.8% 为 `0x0000`（全透明），说明它的内容不在
   我们读取的线性 2B/px 区域，或需要 shader/另一路数据。

这三点与 §6 的下一步一致：优先解 `0x0458/0x0459` 与工作表面合成，而不是继续换
通道顺序。

## 11. 追加：提交队列与描述符布局（静态）

从 kick 栈（`0x73a6e7 → 0x73bd1d → 0x73aa5d`）反查 rm 模块，得到提交链：

| 地址 | 角色 | 关键行为 |
|---|---|---|
| `0x73a470` | 提交入口 | 被 worker `0x73bce0` 调用；内部在 `0x73a6e2` 调 kick |
| `0x73bce0` | worker | `pop` 一个 0x80 字节描述符 → 调 `0x73a470` → 循环 |
| `0x73a9b0` | kick 线程主循环 | 先 `pop`（`0x73b810`），比较 `[desc+8]` 与 `pthread_self()`，再决定提交/回收 |
| `0x73b740` | **push**（生产者→队列） | 把调用者的 0x80 字节描述符拷进队列槽 `base+idx*0x8c+0xc` |
| `0x73b810` | **pop**（队列→调用者） | 从队列槽拷 0x80 字节到调用者缓冲 |

**更正**：之前把 `0x73b740/0x73b810` 的方向看反了；按拷贝方向，`0x73b740` 是入队、
`0x73b810` 是出队。

描述符（0x80 B）在提交时被这样使用：

```text
desc+0x3c  = 命令缓冲 VA
desc+0x40  = 命令缓冲 PA
desc+0x44  = 命令字数（kick 时写入 0x1800）
desc+0x48  = flags（含 0x1000000 时走 0x73c3b0）
desc+0x50  = flags（bit3 走 2D submit 0x73a100）
```

worker 在 `0x73a6d0` 先检查 `[desc+0x44] != 0`，再 `bl 0x73a290`：
`0x1804 = desc+0x40`、`0x1800 = desc+0x44`。

**仍未定位**：向队列 push 的“生产者”不是 rm 模块里的直接调用者（`0x73b740` 只有
worker 自己两处调用）。可能命令缓冲由 GLES/上层直接写环形槽，或 push 被内联/经函数
指针调用。下一步可对 `0x73b740` 下断点，抓调用者 PC（它只在入队时执行，不会像
命令缓冲写那样被 memset 干扰）。


### 11.1 更正：两个函数都是“队列 → 缓冲”方向

按 ARM 调用约定逐条核对 `memcpy(dest=r0, src=r1, n=r2)` 后：

- `0x73b740`：`dest=arg0 缓冲`、`src=队列槽+0xc`，并更新队列头/尾 → **pop**
  （worker `0x73bce0` 入口调它取描述符）；
- `0x73b810`：同样是 `dest=缓冲`、`src=队列槽+0xc`，但不更新头/尾 → **peek/另一队列的 pop**。

因此 §11 表格里把 `0x73b740` 写成 push 是错的；**push（生产者写入）尚未定位**。
对 `0x73b740` 下断点只命中 worker 自己（`LR=0x73bcf3`，栈上 `0x739ecb`、
`0x73aa5d`、`0x748df1`），说明生产者不是通过这个 BL 路径入队的。

下一步建议：在 `0x73b810` 的调用者（`0x73a9c6/0x73aa04`）之外找“写槽 + 更新尾指针”
的代码；或者直接在 worker 拿到描述符后，用描述符里的 `desc+0x3c`（命令 VA）
反查是谁写的这段命令（对 `desc+0x3c` 下写观察点，先命中 memset 就跳过）。


## 12. 命令发射函数与 opcode 表（静态，2026-11-01 续）

找到 GLES 命令的**统一发射函数**：

```text
0x796560(ctx, op, value):
    w = (op << 16) | 0xf000
    append_command(ctx, &{w, value}, 8)   ; 0x796210
```

op 由调用者用 `mov/movw r1,#op` 传入。扫描它的 **47 个调用点**并回溯 r1 立即数，
得到 opcode → 代码语义表（节选，全部有代码上下文）：

| opcode | 代码语义（来自调用点） |
|---|---|
| `0x0010` | 写魔法 `0x12345678` |
| `0x0042/0x0043` | 半宽/半高浮点（`ldr r2,[r7,#0x60]`） |
| `0x0047` | `uxth` 打包 `x0 | y0<<16` |
| `0x0048` | 打包 `x1 | y1<<16` |
| `0x0049` | 区域尺寸 `W | H<<16` |
| `0x0105` | 颜色/状态（`orr` 组合） |
| `0x0106` | 常数 `0x222` |
| `0x010b..0x010f` | 混合/状态位 |
| `0x0110/0x0111` | 标志/移位 |
| `0x0112` | 目标表面地址 `>>4`（`lsrs r2,r2,#4`） |
| `0x0113` | 表面尺寸 |
| `0x0115` | 1 |
| `0x0116` | 源/工作表面地址 `>>4` |
| `0x0117` | 1 |
| `0x0202` | draw（值来自 `[ctx+0x30]`，低 16 位顶点数） |
| `0x0216` | 常量块指针 |
| `0x0450..0x0454` | 纹理级/stage 状态（5 字一组） |

纹理地址发射点 `0x78dcb0` 有 `lsls r3,r3,#3`，再次证实 **`0x0589` 的值 = 纹理 PA>>3**。

### 顶点/属性流

`0x7658f4` 的循环：

```asm
sb = ctx + 0x1540 + 0x30   ; 顶点基址指针表
sl = ctx + 0x1540 + 0x34   ; 顶点数
loop:
  r1 = [sb] + i*0x44       ; 第 i 个顶点（步长 0x44 = 68 字节）
  r2 = 0 ; r3 = 1
  bl 0x796730              ; 发射该顶点的属性
  i++
```

`0x796730` 从 0x44 字节的顶点结构读取，发射 `0x0450f026` + 4 个 32-bit 值（uniform/
attribute 上传）。因此**顶点结构步长是 0x44 字节**，UV 在其中的偏移就是下一步要解的。

### 提交链（生产者侧）

GLES 绘制函数（`0x797xxx`，11 个调用点：`0x797332/797562/797970/797bb6/797cf2/
797e50/797fe0/798132/7985b4/7988b0`）→ `0x739340`（submit_batch）→ `0x73af20`
（push_batch）→ `0x73b188` 用 memcpy 把 0x80 字节描述符批量写入队列槽。

这解释了为什么“生产者”不是独立的 BL 到 pop：**GLES 绘制函数直接批量入队**。

## 14. 更正：`0x796730` 是 uniform 上传，不是顶点属性

在 `0x765914`（`bl 0x796730` 前）下断点，命中时 `r1` 指向的数据是：

```text
r1=00078a48: 07000000 00000000 cdcccc3a 8988083b ...
             ... 696e7653 63726565 6e53697a 65 ...
```

`0x3acccccc = 1.0/640`、`0x3b088889 = 1.0/480`，ASCII 为 **`invScreenSize`**。
因此：

- `0x7658f4` 的循环遍历的是 **uniform 块**（步长 0x44），不是顶点数组；
- `0x796730` 发射的 `0x0450f026` + 4 字是 **uniform 上传**（屏幕尺寸倒数、矩阵等）；
- 之前的“顶点步长 0x44”应更正为“uniform 块步长 0x44”。

这解释了 `0x0450f026` 块里出现 `1/640`、`1/480` 的现象，也说明 **顶点位置/UV 不在 uniform 流里**。
真正决定四边形 UV 的，仍是 `0x0203` 索引缓冲 + 顶点缓冲（地址尚未定位），或 GPU 固定
功能用 `0x0047/0x0048` 矩形直接生成四边形。

**当前两种可能**：
1. 固定功能四边形：纹理整张映射到矩形（我们已这么做）→ 那么文字条纹来自纹理格式/采样；
2. 可编程顶点：顶点缓冲里带 UV → 需要找到顶点缓冲地址。

下一步：在 `0x796560` 发射 `0x0203`（索引缓冲）和 `0x0216`（常量块）的调用点附近，
回溯传入的缓冲对象，定位顶点缓冲；或者直接对 `0x0589` 纹理做 tiling/格式穷举，
用实拍菜单的文字行做 ground truth。


## 15. `0x0216` 常量块内容（uniform buffer）

对 `0x0216` 指向的 `0x2055fd10` 做 32 位/浮点转储，得到的是**着色器 uniform 缓冲**：

```text
0x2055fd10: 00000000 00000000 3f800000 3f800000 3f800000 3f800000 3f800000 00000000
            00000000 3f800000 00000000 00000000 00000000 3f800000 ...
            43f00000 (=480.0) 3f800000 ...
```

即一批 `0/1` 常量、`480.0`（屏幕高度）和矩阵样式的行；与 §14 的 `invScreenSize`
（1/640、1/480）一致。**0x0216 = uniform 常量块**，不是顶点缓冲。

同一批 dump 里：

- `0x2053bb00` 前 128 B 是 `0xff00ff00` 填充，随后就是 `0x0041f000...` 命令字；
- `0x2055f840` 是 16-bit 索引（`0001 0003 0002 ...`）；
- 顶点位置/UV 仍未在这些 dump 中直接出现。

结合 §14，可以确定：**绘制四边形的位置/UV 由 shader 用 uniform（矩形、invScreenSize、
矩阵）计算，或由 GPU 固定功能生成**；`0x0458/0x0459`（模板里 28 字、嵌套列表 56/90 字）
很可能是 **shader 程序二进制**，而不是顶点流。若成立，逐像素正确就需要 DMP shader ISA
解释器，或从 uniform 反推 sprite 变换。

## 16. 当前与实拍菜单的差距（用户提供参考图）

实拍（ILCE-7M3 主菜单）：顶部 6 个 tab（拍摄1/拍摄2/地球/播放/工具箱/星标）、居中标题、
6 行列表（选中行橙色、白字）、底部页码条 + MENU/返回图标。

本轮 `view/GLOBAL_MENU` 帧（`artifacts/global-menu-frame61.png`）：出现 **6 列并排结构**
（与 6 tab 数量一致），左列有橙色块；但文字是横向条纹、tab 方向/排布与实拍不同。
`view/BASE_MENU` 帧（`artifacts/cs0060-center-scale.png`）是全宽橙条的另一视图。

**结论**：几何/视图切换已对上，剩余差距集中在
1) shader/uniform 驱动的 sprite 变换（决定 UV 与文字方向）；
2) 纹理采样/格式/过滤；
3) 视图本身的 tab 布局（6 列 vs 6 行）可能还需要正确的 view 参数（当前 `openView` 只传了 0）。


## 17. GLOBAL_MENU 的 tab 绘制分层（对照实拍）

对 `a7m3-menu1.err` 的 61 条 `SUGI-SD` 记录做分组，前 30 条正好是 **6 个 tab × 5 层**：

| 层 | 纹理 | 尺寸 | 目标屏幕矩形（示例） |
|---|---|---|---|
| 背景渐变 1 | `0x2275b100` | 48×128 | (17,52)-(87,112) / (233,114)-(303,174) … |
| 共享渐变 2 | `0x22413e00` | 640×128 | 同上（整张 640 宽压到 ~70 宽） |
| 选中/装饰 | `0x2275e180` | 112×64 | (0,115)-(105,173)（选中 tab 更宽） |
| 图标 | `0x22767900` / `0x22769d80` / `0x2276c200` / `0x2276e680` … | 72×64 | 每个 tab 唯一 |
| 图标重复 | 同上 | 72×64 | 同矩形（高亮/阴影） |

所有 draw 的 `0x0105` 颜色都是 `0xff00ff70`，**per-tab 颜色不在命令流里**（应由
uniform/shader 或纹理本身给出）。这解释了为什么 6 个 tab 在帧里颜色一致、内容成条纹：
两层 48×128/640×128 渐变被整张拉伸覆盖在图标上，而混合模式（`0x010b..0x010f`）未实现。

新增 `A7M3_SUGI_SKIP_TEX=<hex[,hex...]>` 用于按纹理 PA 跳过指定层，做分层对照：

- 跳过 `0x22413e00`：6 列结构更清楚，但仍有横向条纹（`artifacts/menu-skip640.png`）；
- 再跳过 `0x2275b100`：条纹仍在（`artifacts/menu-skipboth.png`），说明条纹来自
  剩余的 72×64 图标层本身的采样/混合，而不是这两层渐变。

**与实拍对照**：实拍 6 个 tab 是横向排列的彩色圆角块（选中红色），每块内有白色图标+数字；
本帧 6 个 tab 的位置/数量一致，但颜色/内容/方向仍不对。下一步优先实现 `0x010b..0x010f`
的混合状态与 per-tab uniform 颜色，而不是继续猜 UV。


## 18. 嵌套命令列表与属性流（2026-11-01 续）

对 `0x0202` 后 count/address 指向的嵌套列表做全量 opcode 统计（QMP dump）：

| 列表 | 地址 | 大小 | opcodes |
|---|---|---|---|
| A | `0x20556210` | 553 字 | `0450×2 0451×2 0452×2 0453×2 0454×2 0458×5 0459×216 0460×2 0461×4` |
| B | `0x205564b0` | 249 字 | `0450×1 0451×1 0452×1 0453×1 0454×1 0458×2 0459×98 0460×1 0461×2` |
| C | `0x20556460` | 41 字 | `0450×1 0451×1 0452×1 0453×1 0454×1 0458×1 0459×10` |
| D | `0x205565d0` | 25 字 | `0458×1 0459×4 0460×1 0461×2` |

结论：

- 嵌套列表里**没有** `0x0580/0x0589`（纹理绑定只在主缓冲），所以“纹理绑定在嵌套列表、
  我们的纹理状态是错的”这个假设**被否定**；
- 嵌套列表只有 `0x0450..0x0461` = **属性/常量上传**；
- `0x0458` 的值与后续 `0x0459` 条数**不成比例**（`56→68`、`90→30` 等，且数据中有
  零字会打断解析），因此 `0x0458` 更像**起始索引/字节长度/格式**，不是条数。

这与 §14/§15 一致：**顶点位置/UV 不在 uniform、也不在嵌套列表的 0450 流里**，只剩两种可能：
1. `0x0216` 常量块里的矩阵 + `0x0203` 索引 + GPU 固定功能生成四边形；
2. 顶点缓冲在别处（尚未定位）；`0x0459` 是逐顶点属性，但格式/步长未知。

到目前为止，**逐像素文字仍无法从命令流直接还原**；需要继续解 `0x0459` 的 16-bit
属性布局，或实现 DMP shader ISA。
