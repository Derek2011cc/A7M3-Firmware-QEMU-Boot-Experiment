# A7M3 原生菜单的 GPU 绘制链：技术报告

> 目标：在 QEMU `cxd90045` 机器上，让 ILCE-7M3 原厂 App（`im.elf`）打开原生菜单，
> 抓到它提交给 Sugilite GPU 的绘制命令，并把这些命令重放成可看的像素。
>
> 结论摘要：**已经能打开菜单、抓到并在 QEMU 内重放它的 GPU 2D 命令**，但还没有
> 做到像素级正确。CPU 软件绘图路径可以排除；剩余问题是命令构建函数、shader/顶点
> 语义和纹理采样。

---

## 1. 实验环境与启动链

### 1.1 机器与固件

| 项 | 值 |
|---|---|
| QEMU 机器 | ma1co/qemu 的 `cxd90045` |
| guest CPU | ARM32 Cortex-A5（QEMU `cxd90045` 默认 CPU），Linux 3.0.27_nl-rt106+ |
| 内存 | DDR0 1 GiB @ `0x00000000`；DDR1 256 MiB @ `0x80000000` |
| eMMC | 合成 `qemu-emmc-2g.sen.img`，`snapshot=on` |
| 内核/initrd | `vmlinux-console.bin` / `initrd-qemu.img`（由仓库上级的构建脚本生成） |
| LIRO | `av-cam.bin` 预加载到 PA `0x035c6000` |
| GPU | Sugilite，BAR `0xf1000000`（本实验只观察命令环，不模拟真实 GPU） |

启动 harness 的环境变量：

| 变量 | 作用 |
|---|---|
| `A7M3_LIRO_AUTOREADY=1` | **必需**。LIRO 状态寄存器读回全 1，固件才能越过忙等 |
| `A7M3_SEND_SO=<plugin.so>` | 把插件加载到 PA `0x10000000`，guest 命令再 dd 到 `/tmp/v.so` |
| `A7M3_PUMP=<sec>` | 发送命令后继续收串口的秒数 |
| `A7M3_QEMU_EXTRA=<args>` | 追加 QEMU 参数（QMP、`-gdb tcp::1234` 等） |
| `A7M3_SUGI_CMDS=1` | 打开 Sugilite 命令/寄存器 dump |
| `A7M3_SUGI_EXEC=1` | 打开 QEMU 内的命令解释/软件光栅 |
| `A7M3_SUGI_CENTER=1` | 软件光栅使用“居中 1280×960”坐标假设 |
| `A7M3_SURF_DIR=<dir>` | 每次绘制后把目标表面写成 `frame_XXXX.raw` |

### 1.2 在 `im.elf` 进程内执行探针

镜像里预先注入了：

- `/etc/ld.so.preload` → `/etc/shim_io.so`（预加载 shim）；
- `/etc/shim_io.so` = 我们构建的 `shim_uipc.so`（39,228 B）。

shim 在 `execve` 拦截里做两件事：

1. 给 `im.elf` 的 argv 追加 `target=qemu`，让固件走 QEMU 目标分支；
2. 记录 UIPC/ldec/`/dev` 事件，并在 `ioctl(fd, 1, arg)` 上软件实现 Sony LZ77
   解码（`/dev/ldec` 硬件未建模）。

guest 侧命令（`scripts/boot/a7m3-cmds-ui1.txt`）：

```sh
sleep 5
mount -t tmpfs none /tmp
busybox dd if=/dev/mem bs=4096 skip=65536 count=2 of=/tmp/v.so
/usr/bin/scenario.elf ../../tmp/v b:0x01
sleep 60
echo DONE
```

`scenario.elf` 属于 `libtestcmd_scn`，在 `im.elf` 进程内 `dlopen("/tmp/v.so")` 并调用
`scenario_run()`。因此插件与 App 同地址空间，可以直接 `dlsym`、内联 hook、发 UIPC 消息。

> 限制：guest 命令只 dd 2 个 4 KB 页，所以插件必须 ≤ 8 KB。本目录的 manifest 插件
> 都在 4–6 KB。

### 1.3 打开菜单

`viewManagerIf::openView` 是静态成员函数：

```c
viewManagerIf::openView("view/BASE_MENU", 0)
```

用 `dlsym(h, "_ZN13viewManagerIf8openViewEPKci")` 取地址。运行时的证据：

- 返回后 `viewUnified2.so` 已映射（`0x145ee000-0x15050000`，因 ASLR 每次不同）；
- 绘制期间的 `/proc/self/maps` 出现
  `0610d000-0610f000 r--p ... /usr/share/app/viewSettingMenu.uxc`；
- 随后出现 15 次 2D submit（`0x73a100`）和 48 次 GPU kick。

`viewUnified2.so` 是视图管理器/注册表；`view/BASE_MENU` → `viewBaseMenu.uxc`，
菜单内容由 `viewSettingMenu.uxc` 等数据文件驱动。

## 2. 绘制路径：为什么可以排除 CPU 软件绘图

在 `libObj.so` 里对四个 CPU 图形函数下内联钩子（8 字节 `ldr.w pc,[pc,#0]` +
trampoline，见 `scripts/guest/scn_ui.c`）：

| 钩子 | 偏移 | 期望首字 | 整场调用次数 |
|---|---|---|---|
| `GraphicsImage::clear` | `0x611590` | `0xb089b5f0` | 0 |
| `GraphicsImage::copy` | `0x6119bc` | `0x4ff0e92d` | 0 |
| `GRM_gpermFillrect` | `0x64ea98` | `0x4ff0e92d` | 0 |
| `GRM_gpermRectblit` | `0x64ebd2` | `0x4ff0e92d` | 0 |
| 2D submit | `0x73a100` | `0x41f0e92d` | 15 |

（证据：`evidence/04-guest-hooks.txt`；“整场”指钩子装入后到会话结束，钩子一直有效。）

2D submit 的作业记录形如：

```text
UI2D job  src        dst        ... flags  w        h        seq
UI2D 0c2fecec 202e0200 22a80000 00000000 00000004 00000000 00004401 00000280 000001e0 00000030
```

`flags=0x4401`、640×480 的作业把 `0x202e0200` 复制到 `0x22a80000`，很可能是
显示缓冲翻转；`flags=8` 是小的线性 DMA 复制。

结论：**菜单的可见内容由 GPU 命令环 + 2D 引擎产生，不是 CPU 的 GPE 软件绘图**。

## 3. GPU 命令流

### 3.1 提交方式

App 通过 Sugilite 寄存器提交：

- 写 `0x1804` = 命令缓冲区 **物理地址**（字节地址）；
- 写 `0x1800` = `4` 触发 kick；
- 部分路径还会写 `0x1808`/`0x180c` 等（本报告未展开）。

QEMU 模型在 kick 时读取命令缓冲并 dump；`A7M3_SUGI_EXEC=1` 时同时做软件解释。

### 3.2 命令字格式

一个字 = `(opcode << 16) | 0xf000`，后跟 value；部分 opcode 后跟多个字，
`0x0450f026` 这类块的低 16 位是子操作码（例如 `0x0450f026 00000004 3f800000 ...`）。

已解出的 opcode（按在流中出现的顺序）：

| opcode | 含义（工作假设） | 证据 |
|---|---|---|
| `0x0010` | 同步/魔法，value=`0x12345678` | 每个 kick 头部 |
| `0x0041` | 绘制模式，value=2 | 块 37 |
| `0x0042` / `0x0043` | float 320.0 / 240.0（半屏常量） | `43a00000`/`43700000` |
| `0x0044` | 0 | 头部 |
| `0x0047` / `0x0048` | 矩形：四个 int16 `x0,y0,x1,y1` | 动画序列 |
| `0x0049` | 表面尺寸，`0x01e00280` = 640×480 | 所有块 |
| `0x004a` | 0 | 块 37 |
| `0x0100` | `0x100` | 块 37 |
| `0x0101` | `0x71760000` | 块 37 |
| `0x0104` | `0x10` | 块 37 |
| `0x0105` | 颜色/状态，`0xff00ff70` | 块 37 |
| `0x0107` | `0xf40` | 块 37 |
| `0x010a` | `0x0b` | 块 37 |
| `0x010b` / `0x010c` | `0x0f` | 块 22/37 |
| `0x0110` | `0x00040000` | 所有块 |
| `0x0112` | 目标表面地址，value `<< 4` | `0x0202e020` → `0x202e0200` |
| `0x0113` | 表面尺寸，`0x01e00280` = 640×480 | 所有块 |
| `0x0115` | 0 | 所有块 |
| `0x0116` | 源/工作表面，value `<< 4` | `0x02053bb0` → `0x2053bb00` |
| `0x0117` | 1 | 头部 |
| `0x0202` | 绘制；低 16 位是顶点数（4 / `0x7c`） | 块 37 |
| `0x0203` | 索引缓冲区地址（16-bit 索引） | `0x2055f840`/`0x2055f850` |
| `0x0204` | `0x00043201`（属性格式？） | 块 37 |
| `0x0206` | `0x00033333` | 块 37 |
| `0x0208` | `0x0000029e` | 块 37 |
| `0x0209` | `0x241c0c00` | 块 37 |
| `0x020a` | `0x30` | 块 37 |
| `0x020e` | 顶点数（4） | 块 37 |
| `0x0212` | `0x3f` | 块 37 |
| `0x0216` | 常量块地址 | `0x2055fd10` |
| `0x0400..0x0410` | 顶点属性/格式描述 | 块 37 |
| `0x0440..0x0443` | `0x000f0004`/0/`0x38`/`0x63` | 块 37 |
| `0x0450f026` | uniform 块；低 16 位=子索引，后跟 4 个字 | 块 37 |
| `0x0580` | 纹理块开始（9）/结束（1） | 块 22/37 |
| `0x0583` | `0x00010001` | 块 22/37 |
| `0x0584` | `0x11` | 块 22/37 |
| `0x0586` / `0x0587` | 纹理尺寸：高 16=W，低 16=H | `0x028001e0`=640×480；`0x00400038`=64×56 |
| `0x0589` | 纹理地址，value `<< 3` | 见 §3.3 |
| `0x058f` | 4 | 块 22/37 |
| `0x059a..0x05dc` | 0 | 纹理块 |
| `0x05dd` | 7 | 块 22/37 |

*表里的“含义”是工作假设，不是 Sony 文档。下一步应通过命令构建函数确认。*

### 3.3 地址编码（强证据）

`0x0589` 的 value 左移 3 位必须等于 LZ77 解码出的物理目的地址：

| `0x0589` value | `<<3` | 对应资源 |
|---|---|---|
| `0x0445c040` | `0x222e0200` | 640×480 背景（LZ77 614,400 B） |
| `0x044827c0` | `0x22413e00` | 640×72 条带（LZ77 92,160 B） |
| `0x044ee720` | `0x22773900` | 64×56 UI 元素（黑底灰条，用途未确认） |
| `0x044eeab0` | `0x22775580` | 16×16 图标纹理 |

`0x0112` 的 value 左移 4 位必须等于目标表面地址：

| `0x0112` value | `<<4` | 说明 |
|---|---|---|
| `0x0202e020` | `0x202e0200` | 主要 640×480 绘制表面 |
| `0x02053bb0` | `0x2053bb00` | 工作/源表面（`0x0116`） |

这两组移位都不是猜的：与 shim 记录的 LZ77 `m[2]` 目的地址逐字吻合。

### 3.4 一个完整的纹理绘制包（块 37，PA `0x20551480`）

```text
0041f000 00000002       ; mode=2
0042f000 43a00000       ; 320.0
0043f000 43700000       ; 240.0
0047f000 fe20fd80       ; rect x0=-640, y0=-480（见 §3.5 的坐标讨论）
0048f000 fe880280       ; rect x1=640, y1=-376
0049f000 01e00280       ; surface 640x480
0580f000 00000009       ; texture block
0586f000 00400038       ; 64x56
0587f000 00400038
0589f000 044ee720       ; texture PA 0x22773900
0580f000 00000001
0203f000 2055f850       ; index buffer (16-bit indices)
020ef000 00000004       ; 4 vertices
0216f000 2055fd10       ; constant block
0202f000 9000007c       ; draw (low 16 = 0x7c)
0400f000 01000000
0401f000 00000020
...
0450f026 00000004 3f800000 3f800000 3f800000 3f800000
```

块 22（PA `0x2054b310`）是背景绘制：`0x0589=0x0445c040`（640×480），
`0x0203=0x2055f840`，`0x020e=4`。该命令包在 256 字捕获窗口内被截断，说明实际命令
缓冲比 256 字更长；下一次抓取需要把窗口调大。

### 3.5 矩形与动画：坐标空间仍未定

`0x0047`/`0x0048` 是四个 int16：`0x0047` = `x0 | (y0<<16)`，`0x0048` = `x1 | (y1<<16)`。
连续帧里能看到：

```text
块 40: 0047=fe48fff4 0048=fe64000c   -> (-12,-440) - (12,-412)   24x28 小元素
块 22: 0047=015cfd80 0048=01e00280   -> (-640,348) - (640,480)    1280x132 长条
```

- 块 40 的小元素从屏幕上方（y=-440）逐帧向下移动，最终进入可见区；
- 块 22 的长条横跨 x=-640..640，位于 y=348..480（若按 640×480 直接解释，是屏幕底部
  的 132 像素条）。

这有两种解释：

1. **直接 640×480 坐标**：长条是底部菜单栏，小元素从上方滑入。这个解释与
   “菜单栏在底部”的相机 UI 常识一致。
2. **2× 超采样 1280×960 坐标**：`screen=(v+640)/2`，长条仍在底部，小元素变小。
   早期软件渲染默认用了这种“居中”映射，产出的 `c60-rgba4444.png` 结构上更像菜单。

两种解释都还没有被命令构建函数证实；不要把它们当成定论。下一步应优先找构建函数
（见 §7）。

### 3.6 顶点/索引/常量是“嵌套命令列表”，不是平坦数组

从 QMP 转储的 `0x2055f000`/`0x20530000` 区域看，`0x0203` 指向的
`0x2055f850` 是 **16-bit 索引**：

```text
2055f850: 00050004 00070006 00080007 00090008 ...   ; 4,5,6,7,8,9,...
2055f840: 00010000 00030002 00279818 00279818 ...   ; 0,1,2,3, 然后是非常规值
```

而 `0x0202` 之后紧跟着的 count/address 对（块 37）：

```text
00000229 20556210
00000081 2053a4b0
00000029 20556460
000000f9 205564b0
00000019 205565d0
```

这些地址里的内容仍然带 `(op<<16)|0xf000` 的命令字，例如：

```text
20556210: 0458f000 00000038 0459f000 00000000 0459f000 00c40040 ...
2053a4b0: 0460f000 00000000 0461f000 3c1c80e4 0461f000 3c3804e4 ...
205564b0: 0458f000 0000005a 0459f000 00803079 0459f000 00300040 ...
```

工作假设：

- `0x0458` / `0x0459` 是顶点属性写入（`0x0459` 的值包含类似 `00803079`、
  `00300040` 这样的成对 16-bit，可能是 UV/位置）；
- `0x0460` / `0x0461` 是浮点常量写入（`0x0461` 后跟 float 位模式，如
  `3c1c80e4`≈0.00955、`3c3804e4`≈0.01123）；
- `0x0450..0x0454` 是 uniform 块；
- `0x0203` 的索引缓冲把这些属性组合成三角形/四边形。

这意味着**不能**把 `0x0203` 当平坦顶点数组、也不能把整张纹理直接拉伸到矩形：
纹理坐标来自属性流，纹理本身可能是 atlas 或 render target（`0x0445c040`
在几乎每次绘制里都出现，很可能就是主表面/atlas）。

这一点尚未完全证实，但它解释了为什么当前“整张纹理拉伸”的软件重放会得到
看似随机的小图标/文字碎片。

## 4. LZ77 资源解码

相机用 `/dev/ldec` 做 Sony LZ77 解压。QEMU 没有这个硬件，shim 在 `ioctl` 里拦截：

```c
ioctl(fd, 1, arg)
  arg[0] = src VA
  arg[1] = srclen
  arg[2] = dst PA       // 物理地址
  arg[3] = dstlen
  arg[4] = 2
  arg[5] = 3
  arg[6] = 0
  arg[7] = 0x90
```

shim 用自己的 LZ77 解码器（适配自 ma1co/fwtool 的 MIT 实现）解到内存，再通过
`/dev/mem` 写到 `dst`。日志格式：

```text
[U tNNN] LDEC> cmd=00000001 arg=... b= <src> <srclen> <dst> <dstlen> 00000002 00000003 00000000 00000090
[U tNNN] LDEC OK sl=... dl=...
```

已观察到的资源布局（物理地址）：

| 目的 PA | 大小 | 内容/用途 |
|---|---|---|
| `0x222e0200` | 614,400 | 640×480 背景（内容基本是 `0x000f`） |
| `0x2238cb00` … `0x22413e00` | 5 × 92,160 | 640×72 条带/图层 |
| `0x226e0200 + n*0x2000` | 8,064 / 1,920 / 16,128 / 3,840 / 2,560 / 1,024 … | 图标、字形、布局块 |
| `0x2272c200` / `0x2272ca00` | 1,920 | 小图标（LZ77 参数不同：`m4=1`, `m7=0x50`） |

另外一些纹理不是通过 LDEC 写入的（App 自己拷贝/生成）。下表来自**事后 QMP 转储**，
注意纹理内存在运行时复用（见本节末尾）：

| PA | 尺寸 | 备注 |
|---|---|---|
| `0x2276c180` | 96×72 | 线性/平铺视图均稀疏，未解 |
| `0x22773900` | 64×56 | 黑底灰条 UI 元素（用途未确认） |
| `0x22772380` | 56×48 | 已确认：橙色砖纹/图案（未被这 42 个块绑定） |
| `0x22775580` | 16×16 | 图标 |
| `0x22772080` / `0x22772200` | 8×16 | 疑似字形掩码 |

纹理的像素格式（RGBA4444？ARGB1555？索引色？）和 tiling 方式**还没有确定**。
`0x0583=0x00010001`、`0x0584=0x11`、`0x058f=4` 可能与格式/tiling 有关，但未证实。

**重要陷阱：纹理内存在运行时是复用的。** 上表来自 `SCN done` 之后约 40 秒的
QMP `pmemsave`；绘制时刻同一地址可能装着另一张纹理。例如 `0x22773900` 在转储时
是黑底灰条，但软件光栅（在绘制时刻采样）在块 37 画出的却是橙色砖纹区——说明这张
64×56 纹理在绘制后/前被覆盖过。要确定“哪个 draw 用了哪张纹理”，必须在
`0x0202` 绘制时刻抓 `0x0589<<3` 的内容，而不是事后 dump。这个陷阱也解释了
为什么不同实验的纹理截图互相矛盾。

## 5. QEMU 内的软件解释器

### 5.1 位置与构建

- 源码：`qemu/bionz-patched.c`（相对 ma1co/qemu 的 `hw/arm/bionz.c`）；
- 差分：`qemu/qemu-bionz-softrender.patch`；
- 应用：在 ma1co/qemu 树中 `git apply` 后重新 `make -C build-arm`。

补丁增加：

1. `cxd90045_sugi_capture_cmd()`：kick 时读取 `0x1804` 指向的命令缓冲，dump 到 stderr
   （`SUGI-CMDA`），并扫描寄存器/指针（`SUGI-TEX/DST/SRC`）；
2. `cxd90045_sugi_soft_exec()`：解析命令字，维护
   `surf/tex/texw/texh/r47/r48/color`，遇到 `0x0202` 调软件光栅；
3. `cxd90045_sugi_soft_draw()`：按 640×480 RGBA4444 合成，A=低 4 位，source-over；
4. `cxd90045_sugi_surface_dump()`：`A7M3_SURF_DIR` 下逐绘制写 `frame_XXXX.raw`；
5. 2D 引擎 flags=8 的线性 DMA 拷贝（`0x0c18` kick，`A7M3_SUGI_EXEC=1`）。

### 5.2 坐标模式

| 模式 | 环境变量 | 变换 |
|---|---|---|
| 直投 | 默认 | 矩形/纹理坐标原样使用 |
| 半坐标 | `A7M3_SUGI_HALF=1` | `x>>=1, y>>=1`（很快被否定：内容缩到左上 1/4） |
| 居中 | `A7M3_SUGI_CENTER=1` | `screen=((v+640)>>1, (v+480)>>1)`，纹理 1:1 wrap |

三种模式都会产出“结构上像 UI”的帧，但没有一种能让文字可读。**坐标模式仍是待定项**，
不要只用其中一种的产物下结论。

### 5.3 纹理采样（当前实现，已知不完整）

当前 `soft_draw` 按模式采样：

```c
// 直投（默认）：纹理缩放到矩形
u = (x - ox0) * tw / (ox1 - ox0);
v = (y - oy0) * th / (oy1 - oy0);

// 居中（A7M3_SUGI_CENTER=1）：1:1 采样并 wrap
u = (x - ox0) % tw;
v = (y - oy0) % th;

texel = tex[(v*tw + u)];       // RGBA4444，线性寻址
```

这只对“纹理与矩形 1:1（居中模式）”或“简单拉伸（直投）”成立。实际 64×56 纹理
画到 24×28 矩形、640×480 纹理画到 1280×132 矩形时都需要缩放；而且纹理可能是
tiled/索引格式。**这是文字不可读的主要原因之一**。

### 5.4 输出格式

- `frame_XXXX.raw`：640×480×2 B = 614,400 B，little-endian RGBA4444（A 在低 4 位）；
- 转换脚本：`scripts/analysis/gpu/frames2gif.py`；
- 也可以直接用 QMP `pmemsave` 抓 `0x202e0200` 的 0x96000 字节。

## 7. 未解问题与下一步

### 7.1 找到命令构建函数（最高优先级）

目前只知道命令长什么样，不知道 App 里谁写的。三条路线：

1. **QEMU 侧记录 MMIO 写者的 PC/LR**：在 `0x1804`/`0x1800` 的写处理里读
   `current_cpu` 的 `regs[14]`（LR）和 `regs[13]`（SP），dump 调用链；
   再用 `scripts/analysis/libobj/` 里的符号化脚本对照 libObj 偏移。
2. **gdbstub 观察点**：先命中 libc 的 memset/memcpy（已见，见
   `evidence/05-gdbstub-watchpoint.txt`，PC `0x04616350`），需要“越过 memset 后重新
   武装”才能抓到真正的构建者：
   - 命中后删除 `Z2`，`z2` 或单步到 memset 返回，再重新 `Z2`；
   - 或把观察点设在命令环中更靠后的、只有构建者才会写的字。
3. **在 App 内 hook 提交路径的调用者**（`0x73a6e2` / `0x73c8a4` 一线），顺着
   job 结构往上找构建者。

目标：拿到 `dmpNative`/2D 绘制调用的参数（纹理、矩形、混合、采样、顶点缓冲），
而不是继续从命令流反推。

### 7.2 扩大命令抓取窗口

当前日志是 256 字/块（uiprobe3 的构建）；`bionz-patched.c` 已把上限提高到 1024 字。
重新编译并重跑，拿到完整命令包（特别是块 22 的尾部 `0x0202` draw 和后续纹理绑定）。

### 7.3 解码顶点/常量

- `0x0203` 指向的索引缓冲（如 `0x2055f850`，16-bit 索引）；
- `0x0202` 后的 count/address 对指向的嵌套命令列表（如 `0x20556210`、
  `0x2053a4b0`、`0x205564b0`），其中是 `0x0458/0x0459/0x0460/0x0461`
  属性/常量写入；
- `0x0216` 指向的常量块（如 `0x2055fd10`，含 `3f800000`=1.0、
  `41800000`=16.0、`43d60000`=428.0 等）；
- `0x0400..0x0410` 的属性描述；
- `0x0450f026` 的 uniform 块（已知有 `3f800000`=1.0，`4b7fffff`=8388607.5 等）。

这些很可能决定视口变换和纹理坐标，是“文字为什么不可读”的关键。建议先把
**一个**已知矩形（如块 40 的 24×28 小元素）的完整属性流解析出来，和截图对照。

### 7.4 纹理格式与 tiling

- **在绘制时刻抓纹理**（在 QEMU 模型的 `0x0202` 处理里 dump `0x0589<<3` 的内容），
  不要用事后 QMP dump；纹理地址是复用的；
- 用已知的橙色砖纹（转储时刻在 `0x22772380`，56×48）做对照：尝试 RGBA4444/ARGB1555/
  索引色、线性/4×4/8×8 tile，找出能还原出连续砖纹的组合；
- 再用 8×16 字形（`0x22772080`）验证：正确格式下应能看出字符形状；
- 确认 `0x0583/0x0584/0x058f` 是否编码格式/tiling。

### 7.5 补 0x4401 全表面复制

软件解释器目前只执行 flags=8 的线性 DMA；`0x4401` 的 640×480 复制（`0x202e0200`
→ `0x22a80000`）还没实现。补上后可以观察显示缓冲是否被后续命令继续使用。

### 7.6 实时窗口（可选）

当前 QEMU 只有 `none`/`curses` 后端。若需要实时窗口，可重新 configure 带 GTK/SDL，
或参考本仓库 A7C2 的 ramfb 方案；但这不是显示正确性的前提。

## 8. 复现步骤（详细）

### 8.1 准备

1. 按 [../BUILD.md](../BUILD.md) 生成 `vmlinux-console.bin`、`initrd-qemu.img`、
   `qemu-emmc-2g.sen.img`；
2. 在镜像的 FAT12 分区里放入 `/etc/ld.so.preload`（内容 `/etc/shim_io.so`）和
   `/etc/shim_io.so`（`payload/shim_uipc.so`）；`scripts/fat/fat12_add2.py` 可写；
3. 编译插件：

```sh
clang --target=arm-linux-gnueabi -mfloat-abi=soft -fPIC -shared -nostdlib \
      -fuse-ld=lld -O2 -o vui.so scripts/guest/scn_ui.c
```

（`scripts/guest/build-plugins.sh` 会批量编译。）

### 8.2 运行

```sh
A7M3_LIRO_AUTOREADY=1 \
A7M3_SEND_SO=$PWD/vui.so \
A7M3_SUGI_CMDS=1 A7M3_SUGI_EXEC=1 \
A7M3_SURF_DIR=/tmp/a7m3-frames A7M3_PUMP=100 \
python3 scripts/boot/a7m3-shload.py \
  /path/to/qemu-emmc-2g.sen.img demo scripts/boot/a7m3-cmds-ui1.txt 30
```

### 8.3 判据

- 串口出现 `SCN enter`、`UIINFO`、`UIINST`、`SCN done`；
- 出现 `viewSettingMenu.uxc` 的 maps 行；
- 出现 15 条 `UI2D` 记录（含 `0x4401` 640×480 复制）；
- `A7M3_SURF_DIR` 下出现 `frame_*.raw`；`frames2gif.py` 能转出 PNG/GIF。

若没有 `UI2D`，先检查 `openView` 是否成功、`target=qemu` 是否被 shim 追加、
以及 libObj 基址是否取对（用 `dladdr`）。

## 10. 已确认的否定结论（不要重复）

- 菜单绘制**不**经过 `GraphicsImage::clear/copy`、`GRM_gpermFillrect/Rectblit`
  （整场 0 调用）。
- `openView` 的直接调用**确实**打开视图并触发 GPU 提交，但画面不是 CPU 软件 GPE 产生的。
- `0x0589 << 3`、`0x0112 << 4` 的地址编码正确（与 LZ77 目的地址精确吻合），
  不是任意 handle。
- 早期把 `0x0445c040` 当作可读 VA 直接采样是错的：该 VA 在 App 的匿名映射里，
  内容会变；纹理应通过 `0x0589 << 3` 得到的物理地址读取。
- `scn_pg.c`（`vpg.so`）的 VA 采样方法会因映射失效导致 App 崩溃
  （`0x0445d000` translation fault），不要用于长时间运行。
- 居中和直投两种坐标假设都还没有被证明；不要只凭一种产物下结论。
